# r4: decision layer

## 1. Verdict
- **No safe decision-layer gain on 006's probabilities.** Expected LB gain: ~0 (India 0, US 0, France 0). Confidence: high that the current rule is already near the optimum for these probabilities.
- The exact expected-F0.5 rule and calibration add nothing (-0.00004 and 0.00000, measured).
- The one large CV win is a stage-3 context stacker on p006: **+0.0028** (SE 0.00017, 5/5 folds). It is **flagged: it fails the label-free test check.**
  - On test its net extra pairs per S1 are 3.4x (US) and 5.8x (India) the train rate.
  - The US house-conflict share of emitted pairs rises from 7.8% to 10.5%.
  - This is the coherence trap again, now through S1-side context features. Do not ship it.
- The drop-only variant min(p006, p3) keeps only the stacker's removals. It passes CV at **+0.00121** (SE 0.00012, 5/5; India +0.00126, US +0.00118).
  - It cannot emit new pairs, but it drops 3x fewer pairs per S1 on test than on train. The expected LB gain is about +0.0004 to +0.0006 (derived, low confidence).
  - Its own test check (`t2_guard_min.py`) did not finish: it was killed once at 3 GB, then stopped when A's connection dropped. Its test effect is **unconfirmed**.
- Decoy simulation (19% of S1 removed, p006 fixed): the stacker loses -0.00046 (SE 0.00006, 0/5) going from the normal to the decoy-dense graph. The 006 arm of that run was invalid, and the rerun is queued (section 2f).
- Headroom: a perfect prefix length on p006's ranking would score 0.98905 (+0.0146). The heuristic is already the Bayes rule for the marginals, so reaching that needs new information, not a new rule.
- Side finding (measured shift; the LB effect is inferred): the name-frequency features are raw per-split counts. US test has half the S1 of US train, so the same names look about 2x rarer on test (section 2h).

## 2. Evidence
All numbers are measured on the shared 10% sample (220,678 S1, 9.8M pairs, 764,274 gold pairs) using 006's out-of-fold probabilities (p006) and the exact 006 decision (`rk.evaluate` = 0.97443; India 0.97225, US 0.97588). Each diff is the paired rule vs 006: mean per-fold diff (SE, folds positive).

### 2a. Where the missed pairs are
| reason a true pair is not emitted | pairs | mean p006 |
|---|---|---|
| not retrieved (blocking) | 14,837 | - |
| owned, p <= 0.6 (floor or low) | 15,852 | 0.32 |
| pool owned by an S1 outside the sample (higher p) | 8,509 | 0.14 |
| owned, p > 0.6, cut by the prefix | 5,554 | 0.68 |
| S1 answered empty | 786 | 0.26 |
| pool owned by another sampled S1 | 313 | 0.30 |

Emitted: 718,423 TP and 4,849 FP. Ownership has no headroom: 0.16% of the true pairs lost to another owner have p > 0.6 (about 14 pairs), so joint or second-chance assignment cannot matter.

p006 on owned pairs is close to calibrated. In the 0.95+ bin p = 0.9976 and the rate is 0.9980. US is slightly under-confident (p 0.525 -> rate 0.553; p 0.877 -> 0.903). India is slightly over-confident (p 0.526 -> 0.505).

Loss by t (share of the total loss of 0.0256): t=0 0.0014, t=1 0.0044, t=2 0.0052, t=3 0.0052, t=4 0.0043, t=5+ 0.0049. t=1 S1 score 0.918.

### 2b. Exact expected F0.5 (Poisson-binomial DP): no gain
The DP runs over the top 16 owned candidates; the rest goes in as Poisson mass. Optional extra mass: unowned candidate probabilities, and the out-of-fold blocking-miss rate (US 0.052, India 0.091 per S1).

| rule | diff vs 006 |
|---|---|
| exact, owned only, floor 0 | -0.00006 (0.00007, 2/5) |
| exact, owned only, floor 0.6 | -0.00004 (0.00001, 1/5) |
| exact + unowned mass, floor 0.6 | -0.00005 (0.00001, 1/5) |
| exact + unowned + blocking miss, floor 0.6 | -0.00006 (0.00002, 0/5) |
| exact + blocking miss, floor 0, ratio 1.5 | -0.00000 (0.00006, 2/5) |
| heuristic, floor 0 / 0.5 / 0.55 / 0.65 | -0.00003 / +0.00003 / +0.00003 / -0.00022 |
| per-country isotonic (OOF), floor 0.55 / 0.6 / 0.65 | +0.00001 / -0.00004 / -0.00009 |

With calibrated marginals the heuristic 5·Σp₁..ₖ/(Σp+4k) matches the exact Bayes rule under independence, and floor 0.5-0.6 is a flat plateau. Audit 09's ratio rule already lost on 006 (006r: -0.00015).

### 2c. Stage-3 context stacker: large CV gain
A LightGBM (63 leaves, 400 rounds) re-scores each owned pair from p006-derived features only. It is trained out-of-fold inside the sample on the harness folds.
- Pool-side features: p2, the best p006 of any other S1 for the pool record, and margin = p − p2.
- S1-side features: rank k, p of ranks k±1, the sum of higher-ranked p, Σp, counts with p > 0.5 and p > 0.9, log P(no match), the unowned mass, the candidate count, and the count with p > 0.1.

The decision is unchanged: the heuristic prefix applied to the new probabilities.

| feature set | log loss (p006 0.0599) | floor 0.5 | floor 0.6 |
|---|---|---|---|
| all + country flag | 0.0445 | **+0.00282 (0.00019, 5/5)**; India +0.00254, US +0.00300 | +0.00270 (0.00016, 5/5) |
| all, no country flag | 0.0449 | +0.00275 (0.00019, 5/5) | +0.00264 (0.00017, 5/5) |
| S1-side only | 0.0471 | +0.00195 (0.00021, 5/5) | +0.00187 (0.00017, 5/5) |
| pool-side only (p, p2, margin) | 0.0606 | -0.00004 (0.00011, 2/5) | -0.00002 (0.00004, 3/5) |

The gain comes from S1-side context: the probability of the next candidate is the top feature after p itself. By true count: t=0 -0.00001, t=1 +0.00016, t=2 +0.00052, t=3 +0.00063, t=4 +0.00061, t=5+ +0.00080. So it mostly adds moderate-probability candidates to S1 that already have several strong matches.

Leakage check: all inputs are OOF p006, and a competitor's p006 carries no pool identity (min_data_in_leaf 200), so this is plain stacking. The failure below is a shift problem, not a leak.

### 2d. Test check (all 3 countries, owned test pairs, `rk.test_guard`)
| | per S1 US / India / France | empty rate US / India / France | house conflict US / India / France |
|---|---|---|---|
| 006 (reproduces the brief exactly) | 3.329 / 3.316 / 3.448 | 5.89 / 5.85 / 4.99% | **7.79 / 16.78 / 1.80%** |
| stacker, floor 0.6 | 3.451 / 3.437 / 3.495 | 5.85 / 5.82 / 5.04% | **10.47 / 18.07 / 2.85%** |
| stacker, floor 0.5 | 3.453 / 3.439 / 3.497 | 5.76 / 5.70 / 4.86% | 10.49 / 18.08 / 2.87% |

Pairs the stacker adds or drops vs 006 (floor 0.6), train sample vs test:
| | train added per S1 (precision; conflict) | test added per S1 (conflict) | train dropped per S1 (precision) | test dropped per S1 (conflict) |
|---|---|---|---|---|
| US | 0.051 (0.854; 71.0%) | 0.127 (82.2%) | 0.015 (0.468) | 0.005 (49.0%) |
| India | 0.044 (0.850; 52.7%) | 0.130 (52.6%) | 0.023 (0.534) | 0.009 (41.3%) |
| France | - | 0.078 (55.0%; kept pairs 1.7%) | - | 0.030 (17.5%) |

On train, added pairs are mostly true matches with noisy house numbers (85% precision), so a high conflict share alone would not condemn them. The problem is volume. On test the stacker adds 2.5-3x as many pairs per S1 as on train, and makes 3.4x (US) and 5.8x (India) the net additions. If the extra US additions beyond the train rate are split out, their implied conflict share is about 90% (derived). These look like other branches of the same chain whose own S1 is absent from test: the decoys the brief warns about. **Flag: CV win, test-shift loss. Do not ship.**

### 2e. Drop-only and add-only variants (CV measured)
| variant (vs 006) | floor 0.6 | floor 0.5 |
|---|---|---|
| full stacker p3 | +0.00270 (0.00016, 5/5) | +0.00282 (0.00019, 5/5) |
| **drop-only min(p006, p3)** | **+0.00121 (0.00012, 5/5)**; India +0.00126, US +0.00118 | +0.00127 (0.00015, 5/5) |
| add-only max(p006, p3) | +0.00147 (0.00007, 5/5) | +0.00154 (0.00013, 5/5) |

The drop-only variant passes CV and only lowers probabilities, so it cannot boost decoys. On test the stacker's drops are few (US 0.005 and India 0.009 per S1, vs 0.015 and 0.023 on train). The expected LB gain is therefore well under the CV +0.0012: about +0.0004 to +0.0006, scaling the CV gain by the test/train drop rate (derived, low confidence). Its test check (`t2_guard_min.py`) and the decoy simulation (`d3lite.py`) are below if they finished in time.

### 2f. Decoy-dense simulation and oracle headroom
Method (`d1_build.py`, `d3lite.py`): remove 19% of all train S1 (hash seed 0). 178,766 sampled S1 remain and are scored in both worlds. Their now-orphaned pool records become decoys: owned negatives among the scored S1 rise from 221,899 to 379,468 (x1.71), while owned positives stay at 600k. The pool-side graph and competition features of the remaining pairs are recomputed (`d_feats_s0.parquet`). The first run holds p006 fixed and recomputes ownership, rivals and the stacker's context.
- Stacker, decoy world minus normal world (same S1, valid): floor 0.6 **-0.00046** (SE 0.00006, 0/5); floor 0.5 -0.00045 (SE 0.00005, 0/5).
- The 006 arm of that run was invalid: rows were not re-sorted after joins, so the prefix sums were wrong. It is fixed and rerunning (`d3lite_s0.log`). Audit 09's fixed-probability simulation lost only about -0.00008 for floor 0.6, so the stacker loses roughly 5x more from decoys (derived). That is consistent with the test check.
- The full simulation (re-scoring stage 2 on the recomputed features, `d2_score.py`, `d3_eval.py`) was not run: out of time on a saturated queue. `d3_eval.py` has the same sort bug in its 006 arm and needs the `d3lite.py` fix before use.

Oracle headroom (`a4_oracle.py`): perfect prefix length on p006's order 0.98905 (India 0.98787, US 0.98983). On the stacker's order it is 0.98897, so the stacker does not improve the ranking. A perfect subset of owned pairs gives 0.99044. The rule is at its Bayes limit for these marginals (2b). The remaining k-selection gap of about 0.0146 can only close with better pair evidence, not with the decision rule.

### 2g. No per-source structure to exploit (measured)
True S2 and S3 match counts per S1 are nearly independent: corr 0.12, max 5 and 6, means 1.65 and 1.75. S1 with s2 strong S2 and s3 strong S3 candidates (p > 0.5) have 1.03-1.04x as many true matches per source. So a source-aware count model has no cap or balance to exploit (`a5_src.py`).

### 2h. Side finding: name-frequency scale shift (measured)
| | S1 | mean nf_s1_s1 | name shared by >= 2 / >= 6 S1 | mean nf_s1_pool |
|---|---|---|---|---|
| US train / test | 1,323,633 / 663,106 | 1.594 / 1.380 | 47.7% / 39.9%, 23.4% / 19.2% | 2.204 / 2.041 |
| India train / test | 883,188 / 809,986 | 1.971 / 1.935 | 54.0% / 53.2%, 36.3% / 35.9% | 2.746 / 2.780 |
| France test | 259,452 | 1.520 | 47.6%, 25.8% | 2.342 |

`er_feat2` counts are raw per split. A US chain name seen 10 times on train is seen about 5 times on test, so the model sees it as more distinctive exactly where decoys are denser. That is plausibly part of the US gap between CV and LB (inferred, not measured). Fix for the feature lanes: count per million S1 of the country, i.e. log1p(n·1e6/N_country). Pool/S1 on test is 5.82 India, 5.76 US, 5.53 France (train 4.68).

### 2i. Name-frequency shift simulation (halved-US counts), on machine D
Question: does the model lose when US name counts come from a country half the size, as on test? Does per-country-size normalisation fix it?

Method (`n2_nfshift.py`, in-sample stage-2 recipe = pb: `rk.BASE_FEATS`, `rk.PARAMS`, 600 rounds, 5 harness folds, 1 thread):
- Counts are rebuilt from `norm/train_{s1,pool}` `name_join` per country, exactly as in `er_feat2`. The script asserts that the full counts reproduce the cached nf_*.
- "Halved US" counts: keep 50% of US business clusters (an S1 together with its gold pool records) and 50% of unmatched US pool records, by hash. The scored S1 and its own cluster are always counted, and the scored pool record always counts itself, because on test a record and its true partners are present. India is unchanged.
- Arm A: train on normal nf_*, predict the held-out fold with normal (A) and with halved-US (As) counts.
- Arm B: nf = log1p(n·1e6/N), with N the country's S1 total for S1 counts and its pool total for pool counts. Train and apply in B; the halved world uses the halved totals (Bs).
- Limit: stage-1 probabilities, and the cp_* and cs_* features built from them, are held fixed. On test they would also shift, so this understates the effect.

## 3. Build spec
- **Decision rule: keep 006 as is** (heuristic prefix + floor 0.6). Do not implement the exact rule or calibration: no gain.
- **Stage-3 stacker: do not ship the full version.** The drop-only variant passed CV (+0.00121). If its test check (`t2_guard_min.log`) shows the emitted count per S1 and the house-conflict share at or below 006, it is a small, safe add-on.
  - New `src/er_stack3.py`: `feats()` as in `research/r4/st3.py` on the full graph (rival=None). Train on `cache/oof/006_stage2` (5-fold OOF for CV, then a full fit). Apply to `test_006_stage2`. Emit min(p006, p3), then decide.
  - Compute: about 30 min on one 8-core machine (98M pairs to about 10M owned pairs; 5 x 400 rounds). Peak about 12-16 GB.
  - Needs the human's approval (new harness step).
- Any future rescoring that uses S1-side context (the coherence family) must pass `rk.test_guard` with a per-S1 added-pairs ratio, test vs train, near 1. That is a sharper alarm than the conflict share alone.

## 4. Risks and interactions
- The S1-side context reproduces the coherence trap. The generator gives test S1 look-alike pool records whose owner is missing, and in train such a record almost always has its owner present.
- Any CV gain from "this S1 already has many strong matches, so accept one more" should be assumed unsafe until the test check passes.
- If the stage-2 model is retrained (e.g. name-specificity features), the calibration conclusions still hold, but re-run `a2_exact.py` and `a3_stack.py` on the new OOF.
- France: no labels. The stacker added 0.078 pairs per S1 there, with 55% conflict against 1.7% for kept pairs. That is another sign it emits decoys.
