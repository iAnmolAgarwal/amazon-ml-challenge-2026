# r8: retrieval and the India residual

Status: in progress (partial results; updated as measured). All numbers train-only unless marked test (label-free).

## 1. Verdict
(provisional) Retrieval is a small lever: the whole blocking gap is worth at most +0.0055 LB (every missed pair recovered and accepted).
**Reverse top-1 retrieval** (+0.14 pairs per S1) plus **one new exact key** (name prefix + house) recover ~35-45% of it:
about **+0.0015-0.002 LB** (US +0.001-0.0015, India +0.002-0.0025; derived from oracle gains x measured acceptance, medium confidence).
The India native-script residual is worth **0**: the "test-only" words are train distractor-only words that 006 already rejects.

## 2. Evidence

### 2.1 India native-script residual (measured, all India records, train and test)
- After the dictionary no India S1 name and no India address (train or test) keeps a native token. Residual native names exist only
  on pool records: train 64,020 (1.55% of India pool), test 121,031 (2.57%).
- They are the **same 171 tokens** in train and test (19 shop words x 9 scripts: motors, stores, agencies, jewellers, general, bakery,
  provision, sweets, pharmacy, medicals, automobiles, traders, hardware, garments, steel, electronics, furniture, restaurant, textiles).
  None is test-only; er_dict never maps them because they never occur in a gold pair.
- **Gold rate of these pool records in train: 0 of 64,020** (fully mapped native names 0.800, Latin names 0.742): pure distractors.
  006 already rejects them (max probability p99 0.0005 train OOF, 0.0003 test; none above 0.5). Test/train count ratio 1.9x = the decoy excess.
- **Mapping them (earlier item c) is worth 0 and would remove a perfect distractor signal** (`nonlatin_name_p`). Do not build it.
- Native addresses: all 17 state tokens map; 3 multi-word states map to one word (Tamil Nadu -> "nadu", Andhra Pradesh -> "andhra",
  West Bengal -> "bengal"); low-IDF state words, so no measurable lever.

### 2.2 India house-number parse noise (measured, 23,788 retrieved + 7,997 missed India gold pairs)
- 16.7% of retrieved India gold pairs have conflicting parsed house numbers; in **64% of those (10.7% of all) the S1 house is among the
  pool's numbers** (US: 8.5% conflicts, only 0.25% of this kind). This drives India's 16.8% house-conflict share on test.
- One generator form is a template plus a random number before the real one ("H.NO 930 131" vs S1 "131, Garg Plaza"). A parse fix for
  it (hfix.py: drop the first number of "template N M") applies to only 1.6% of India gold pairs: house_eq 0.674 -> 0.686 (gold),
  0.1475 -> 0.1495 (non-gold candidates with p006 > 0.01), 0.298 -> 0.327 (missed gold). The rest are multi-number ambiguities on
  either side, so a symmetric "house found among the other side's numbers" feature (r1 `h1_in_p`) is the right tool, not a parse fix.
- Name-operator vocabularies (decoy modifiers group/holdings/industries/ventures... never on true matches; fillers center/services/partners
  on true matches) reproduced on the quick subset; they confirm r1/r9, whose lanes own the features.

### 2.3 Retrieval: the 2% of never-candidate gold pairs (measured, full 10% sample)
- US 132,451 S1 / 458,065 gold / 6,840 missed (1.49%), oracle 0.99549; India 88,227 / 306,209 / 7,997 (2.61%), oracle 0.99188.
  India's model loss (oracle - CV) equals the US one (0.0197); **India's extra gap vs US is entirely retrieval**.
- Missed vs retrieved gold pairs: pool address empty US 0.468 vs 0.040, India 0.321 vs 0.032; same name_join US 0.064 vs 0.618,
  India 0.197 vs 0.740 (India misses sit in oversized same-name blocks); same house US 0.207 vs 0.788, India 0.298 vs 0.675.
- Not causes: native script (9.4% of India misses vs 17.9% of retrieved pairs), acronyms (0 misses have an initials relation).

### 2.6 How much of the oracle gain is realized
- **Acceptance proxy (measured, exact 006 decision):** gold pairs that are candidates only through the existing keys (word rank > 40)
  are accepted at 0.918 (US, 2,620) and 0.893 (India, 2,795) vs 0.956 / 0.963 for word-retrieved gold; the 446k / 526k key-only
  pairs yield only 28 / 57 emitted decoys. So realized gain is about 0.85-0.9 x oracle gain (derived).

## 3. Build spec
- `src/er_block.py`: run with `--rev-k 1` (already coded: each pool record's top-1 S1, flag `k_rev`) and add key `k_p6h` in
  `key_pairs` = first 6 letters of `name_join` + "|" + `house` (both sides; `name_join` >= 6 chars, house present; cap 50);
  keys `k_sk,k_skh,k_fl` are already coded. Add the new flags to the stage-1 feature list (they also enter `n_keys`).
- Growth: reverse top-1 +0.14 (US) per S1; p6h +2.0 / +3.2; v3 keys +2.1 / +2.2 (US / India); total about +9-12% pairs.
- Compute: the reverse pass costs about one forward pass (10M pool queries against the S1 index, 8 threads); keys take under a minute.
  Then features (~1.2 h per split), stage-1 CV + feat4 + stage-2 CV (~2.5 h). Stage-2 CV already peaks at 61.7 of 64 GB, so +10%
  pairs needs the loader fix noted in STATUS (or 50%-entity training).
- Go/no-go: paired CV on the full chain (stage 2 included) plus the label-free test guards.

## 4. Risks and interactions
- New candidates include near-duplicate decoys (same name prefix and house); run the test guards (house-conflict, near<=20 share).
- Stage-2 competition features change on the larger graph; stage-1 evidence is a proxy.
- A house relation that reads the India "template + random number" (r1 `h1_in_p`) raises the value of recovered India pairs;
  name-operator features (r1/r9) reject the modifier decoys that new keys pull in.
- Queue note: `rk/run.sh` can fail inside its accounting loop (a .job file removed between the liveness check and `head`) and then
  run the job while still holding the queue lock; this blocked A's queue for ~10 min around 12:05-12:15 UTC (r8's xtok job).
